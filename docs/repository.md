# TrashRadar — Repository & Code Organization

> Статус: Draft v1.0
> Дата: 2026-07-08
> Базується на: [product.md](product.md) v1.1, [ui.md](ui.md) v1.1, [architecture.md](architecture.md) v1.0, [features.md](features.md) v1.0, [tasks.md](tasks.md) v1.0
> Роль документа: організація репозиторію, шари коду, конвенції. Описує *де що живе і що від чого залежить* — без коду.

---

## 0. Принципи організації

1. **Репозиторій — відбиток архітектури.** Двопроцесна модель architecture.md (нативне ядро + webview-UI) видима з першого погляду на корінь: `core/` і `ui/` — два світи, з'єднані лише контрактом IPC.
2. **Шари — фізичні, не уявні.** Domain / Application / Infrastructure — окремі одиниці компіляції (Rust-крейти), а не папки за домовленістю. Заборонену залежність неможливо додати непомітно: вона не збереться.
3. **Масштабування додаванням, не переписуванням.** Нова категорія-детектор, нове джерело превью, майбутній macOS-порт чи headless CLI — це *новий модуль поруч*, а не правки в наявних. Точки розширення визначені заздалегідь.
4. **Монорепозиторій.** Ядро, UI, декларативні дані детекторів, документація і бенчмарки версіонуються разом: одна гілка = один узгоджений стан продукту.

## 1. Структура репозиторію (корінь)

```
file-reaper/
├── docs/                    # продуктова і технічна документація (цей пакет)
├── core/                    # Rust workspace — Core Engine (розділи 3–5)
├── ui/                      # React + TypeScript — UI Layer (розділ 6)
├── contracts/               # контракт IPC: схеми команд і подій (єдине джерело правди)
├── registry/                # декларативні дані: локації кешів/темпів, маркери dev-артефактів
├── assets/                  # іконки, ресурси інсталятора
├── benches/                 # еталонні набори і сценарії бенчмарків (цілі architecture.md §15)
├── tests/                   # наскрізні (E2E) тести: скан → категорії → reap → restore
├── scripts/                 # службові сценарії збірки/релізу
└── .github/                 # CI-конвеєри, шаблони PR та issue
```

Пояснення нетипових директорій:

- **`contracts/`** — описи всіх IPC-команд і подій у форматі, з якого генеруються типи для обох сторін (Rust і TypeScript). Зміна контракту — це зміна файлу тут, і вона автоматично «розходиться» по обох світах. Ручна синхронізація типів заборонена.
- **`registry/`** — дані, не код (architecture.md §6): відомі Temp-локації, кеші програм, маркери структурних детекторів. Оновлюються без релізу ядра; мають власні валідаційні тести.
- **`benches/`** — бенчмарки винесені з ядра, бо їхні еталонні сценарії спільні для кількох крейтів і для CI-політики «регрес швидкості блокує реліз».

## 2. Структура директорій (деталізація)

### 2.1. `core/` — Rust workspace

```

├── app/                     # Application Layer — use cases і порти (розділ 4)

### 2.2. `ui/` — React-застосунок

```
ui/
├── src/
│   ├── ipc/                 # клієнт команд/подій, згенеровані типи з contracts/
│   ├── store/               # стан як проєкція стріму подій Core
│   ├── design/              # токени теми, типографіка, базові примітиви
│   ├── components/          # спільні компоненти: плитка, віртуальна сітка, тости, чипси
│   ├── features/            # екрани-фічі, по директорії на екран:
│   │   ├── cleanup-summary/ #   головний екран з цифрою
│   │   ├── category/        #   сітка категорії + рядок детектора
│   │   ├── duplicates/      #   подання групами
│   │   ├── quarantine/      #   карантин
│   │   ├── reap-flow/       #   оверлей підтвердження REAP
│   │   ├── live-preview/    #   двомоніторний режим ★
│   │   ├── details-panel/   #   панель деталей
│   │   └── settings/        #   налаштування
│   ├── hotkeys/             # реєстр гарячих клавіш і контекстів

Правило для `features/`: фіча може імпортувати `components/`, `design/`, `store/`, `ipc/`, `hotkeys/` — але **не іншу фічу**. Спільне між фічами спускається у `components/` або `store/`. Це тримає екрани видаляємими і незалежними (кожен epic E10–E18 з tasks.md живе у своїй директорії).

## 3. Domain Layer (`core/domain`)

**Що це:** словник продукту, виражений у типах. Жодного I/O, жодних залежностей на ОС, БД, Tauri — чиста логіка, що компілюється й тестується будь-де.

**Вміст:**

| Група | Приклади понять |
|---|---|
| Сутності | Запис файла (кандидат), Категорія, Вердикт детектора, Група дублікатів, Запис Quarantine, Операція (reap/restore/purge batch) |
| Value objects | Розмір, Вік, Шлях (нормалізований), Рівень безпечності (safe-to-bulk / review-recommended), Статус карантину, TTL |
| Доменні правила | Політика «який дублікат залишити»; правила унікалізації файла між категоріями (чесна цифра); інваріанти життєвого циклу карантинного запису (quarantined → restored | purged, без інших переходів); правила guard-list |
| Доменні події | «файл став кандидатом», «вердикт змінено», «запис карантину прострочено» |

**Ключова властивість:** усе, що в product.md названо «правилом продукту» (двофазність видалення, чесний підрахунок, рівні безпечності), живе тут — і тестується юніт-тестами без диска. Помилка в цих правилах — найдорожча, тому вони ізольовані від найнестабільнішого коду (I/O).

**Заборонено в Domain:** файлова система, SQLite, WinAPI, потоки/async-рантайм, серіалізація IPC, логування у файли.

## 4. Application Layer (`core/app`)

**Що це:** оркестрація use case-ів. Знає *що* треба зробити і *в якому порядку*, але не знає *як* фізично (це справа Infrastructure).

**Вміст:**

| Група | Відповідальність |
|---|---|
| Use cases | «Просканувати томи», «Перерахувати категорію з новими порогами», «Позначити все у safe-категорії», «Reap batch», «Restore batch», «Purge прострочене», «Запит вікна сітки» |
| Оркестратори | Ферма детекторів (прогін потоку індексу), каскад дублікатів (щаблі 1→2→3), Aggregator (живі цифри), планувальник фонових модулів (architecture.md §13) |
| **Порти (traits)** | Оголошені тут, реалізовані в Infrastructure: ДжерелоСкану, Індекс, СховищеПревью, КарантиннаFS, Хешер, Годинник, ДжерелоНалаштувань |
| Політики виконання | Пріоритети черг (P0–P3 превью), тротлінг подій, ліміти I/O на том, кооперативна відміна |

**Ключова властивість:** Application залежить **лише від Domain**. Усі зовнішні можливості — через порти. Наслідок: кожен use case тестується з фейковими адаптерами (віртуальна FS з `testkit/`) — включно з найстрашнішими сценаріями типу «краш посеред reap» (T-156), які на реальному диску відтворювати повільно і боляче.

Тут само живе **склад детекторів**: кожен детектор — окремий модуль, що реалізує контракт детектора (T-036). Нова категорія (roadmap: власні категорії, геймерські детектори) = новий модуль у цій директорії + запис у реєстрі, нуль правок в оркестраторі.

## 5. Infrastructure Layer (`core/infra/*`)

**Що це:** адаптери портів до реального світу. Кожен адаптер — окремий крейт з вузькою відповідальністю (перелік — у 2.1).

**Правила шару:**

- Адаптер реалізує порт з Application і **не містить бізнес-рішень**: `scan-mft` не знає, що таке «кандидат»; `quarantine-fs` не знає, чому файл видаляють. Вони вміють лише свою механіку — швидко і надійно.
- Взаємозамінність за портом: `scan-mft` і `scan-walk` — дві реалізації одного порту ДжерелоСкану; вибір робить Application (T-028). Так само превью-джерела (кеш / Shell / власна генерація) — ланцюжок реалізацій одного порту.
- Платформозалежний код (WinAPI) концентрується в `platform-win` і адаптерах, що його потребують. Майбутній macOS-порт (roadmap Фаза 4) = нові крейти `scan-apfs`, `platform-mac` поруч — Domain, Application і UI не змінюються.
- Небезпечні можливості ізольовані: право на деструктивні операції з FS має **лише** `quarantine-fs` (шлюз з architecture.md §8). Жоден інший інфраструктурний крейт не лінкує API видалення — це перевіряється залежностями крейтів і рев'ю.
- Найнестабільніший код (декодери медіа у `preview/`) живе за бар'єром ізоляції збоїв (T-074) і не тягне залежності в інші крейти.

**`core/shell` (Tauri-оболонка)** — технічно теж інфраструктура, але з особливою роллю: єдине місце, де світ UI зустрічає світ Core. Містить лише: створення вікна, реєстрацію IPC-команд/подій за контрактами з `contracts/`, життєвий цикл застосунку. Бізнес-логіки — нуль; що менший `shell`, то дешевша потенційна міграція оболонки (пом'якшення ризику з architecture.md §11.2).

## 6. UI Layer (`ui/`)

**Що це:** тонкий реактивний клієнт. Вся правда — у Core; UI лише проєктує стрім подій у пікселі та перетворює жести користувача на команди.

**Внутрішні шари UI (зверху вниз):**

| Шар | Відповідальність | Залежить від |
|---|---|---|
| `features/*` | Екрани: композиція, сценарії взаємодії | components, store, hotkeys, design |
| `components/` | Перевикористовувані блоки без знання про екрани (плитка, сітка, тост) | design, store (читання) |
| `store/` | Стан = проєкція подій Core + оптимістичні позначення з відкатом | ipc |
| `ipc/` | Команди/підписки, згенеровані типи контракту | contracts (генерація) |
| `design/` | Токени теми, типографіка — жодної логіки | — |

**Правила шару:**

- UI **ніколи** не звертається до файлової системи, шляхів, диска — навіть «безневинно» (перевірити існування файла). Немає такої можливості за контрактом, і не повинно з'явитись.
- Дані великих списків — лише віконними запитами (T-014/T-101); UI не тримає «всю категорію» в пам'яті.
- Оптимістичні оновлення: позначення відображається миттєво, відкат — за відхиленням Core (контракт з architecture.md §14).
- Кожен екран ui.md = одна директорія у `features/` = один epic у tasks.md — трасованість «дизайн → код → задачі» без картки-словника.

## 7. Naming Convention

### 7.1. Rust (core)

| Об'єкт | Стиль | Приклад-шаблон |
|---|---|---|
| Крейти | kebab-case, префікс групи | `infra/scan-mft`, `infra/index-sqlite` |
| Модулі, функції, поля | snake_case | `scan_volume`, `last_access_at` |
| Типи, трейти | PascalCase; порти — за роллю, без суфікса «Manager/Helper» | `ScanSource`, `QuarantineStore`, `Verdict` |
| Помилки | PascalCase + суфікс `Error`, по одному типу на крейт-межу | `IndexError` |

### 7.2. TypeScript (ui)

| Об'єкт | Стиль | Приклад-шаблон |
|---|---|---|
| Компоненти | PascalCase, файл = ім'я компонента | `FileTile`, `ReapBar` |
| Хуки | префікс `use` | `useCategoryWindow`, `useArmedAction` |
| Директорії | kebab-case | `live-preview/`, `cleanup-summary/` |
| Утиліти, змінні | camelCase | `formatSize` |

### 7.3. Контракт IPC (`contracts/`)

- Команди — дієслівні, простір імен через крапку: `scan.start`, `category.set_threshold`, `quarantine.restore_batch`.
- Події — іменникові стани у минулому/тривалому: `scan.progress`, `category.updated`, `quarantine.entry_expired`.
- Правило: назва команди відповідає use case-у Application, назва події — доменній події. Контракт читається як зміст продукту.

### 7.4. Загальні заборони

- Жодних абревіатур поза словником проєкту (словник: MFT, USN, TTL, IPC, reap, keep, purge).
- Термінологія коду = термінологія product.md: у коді існують «candidate», «category», «detector», «reap», «quarantine» — і не існує «trash», «junk», «cleaner» як типів (щоб код не розповзся у другу термінологію).

## 8. Commit Convention

**Формат: Conventional Commits.**

```
<тип>(<область>): <підсумок у наказовому способі>

<тіло: що і чому, якщо неочевидно>

Refs: T-###
```

- **Типи:** `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `chore`.
- **Області = карта репозиторію:** `domain`, `app`, `scan`, `index`, `preview`, `quarantine`, `hash`, `shell`, `contracts`, `registry`, `ui/<фіча>` (напр. `ui/live-preview`), `bench`, `ci`.
- **Прив'язка до беклогу:** кожен коміт з типом `feat`/`fix`/`perf` посилається на задачу з tasks.md (`Refs: T-079`). Історія відповідає декомпозиції; закриття задачі трасується до комітів.
- `perf` — окремий тип свідомо: продуктова політика «швидкість — фіча» означає, що перф-зміни мають бути видимі в історії та changelog.
- Breaking-зміни контракту IPC позначаються `!` (напр. `feat(contracts)!: …`) і вимагають синхронного коміту в обох світах.
- Changelog генерується з комітів — тому підсумок пишеться мовою результату («prevent reap of guarded paths»), не процесу («fix bug»).

## 9. Git Branch Strategy

**Модель: trunk-based з короткоживучими гілками.** Команда мала, продукт до бети — важкі git-flow церемонії не окупляться.

| Гілка | Роль | Правила |
|---|---|---|
| `main` | Єдиний trunk; завжди зелений і збирається в інсталятор | Захищена: тільки через PR; обов'язковий CI (збірка, тести, бенчмарки) + 1 рев'ю |
| `t###-<слаг>` | Робоча гілка однієї задачі з tasks.md (напр. `t079-transactional-reap`) | Живе ≤ кількох днів; merge через squash — 1 задача ≈ 1 коміт у trunk |
| `release/beta-N` | Зріз для приватної бети (Milestone M6) | Тільки cherry-pick фіксів з `main`; тег версії на кожну збірку |

Доповнення:

- Іменування гілки від ID задачі — пряма трасованість tasks.md → гілка → PR → коміт.
- Незавершена робота, що мусить жити в `main` (епіки на кілька задач), ховається за прапорцями можливостей — trunk завжди релізний.
- Теги: semver з нульовою мажорною до публічного релізу (`v0.x.y`); реліз-ноти — з changelog комітів.
- Бенчмарк-гейт: PR, що погіршує метрики §15 понад поріг, не мержиться (T-154) — це гілкова політика, не лише добра воля.

## 10. Dependency Rules

Головне правило — **напрямок залежностей завжди всередину, до Domain:**

```
        UI (webview)
         │  лише contracts/ (типи IPC) — більше нічого
         ▼
      core/shell (Tauri: вікно + міст IPC)
         │
         ▼
      core/app  ──────────►  core/domain
         ▲    (use cases,        (чиста модель,
         │     порти)             нуль залежностей)
         │ реалізують порти
      core/infra/*  ───────►  core/domain (типи)
```

Матриця «кому що можна»:

| Звідки \ Куди | domain | app | infra/* | shell | contracts | ui |
|---|---|---|---|---|---|---|
| **domain** | — | ✖ | ✖ | ✖ | ✖ | ✖ |
| **app** | ✔ | — | ✖ (лише порти) | ✖ | ✖ | ✖ |
| **infra/*** | ✔ (типи) | ✔ (порти) | ✖ між собою* | ✖ | ✖ | ✖ |
| **shell** | ✔ | ✔ | ✔ (складання) | — | ✔ | ✖ |
| **ui** | ✖ | ✖ | ✖ | ✖ | ✔ (генеровані типи) | — |

\* Виняток: будь-який інфраструктурний крейт може залежати від `platform-win` (спільні WinAPI-обгортки) і `testkit` (тільки в тестах). Горизонтальні залежності `infra`-крейтів один від одного заборонені — спільне піднімається у порт або у `platform-win`.

Наслідки правил (навіщо це все):

1. **Domain без залежностей** → правила продукту тестуються за мілісекунди і не ламаються від оновлення будь-якої бібліотеки.
2. **App знає лише порти** → будь-який сценарій, включно з крашем посеред reap, відтворюється на фейковій FS у CI.
3. **Infra ізольовані один від одного** → декодер превью фізично не може зачепити карантин; право видаляти — лише в `quarantine-fs` (інваріант D4 architecture.md, забезпечений компілятором).
4. **UI бачить лише contracts** → «UI не може торкнутися диска» — не домовленість, а відсутність такої можливості в графі залежностей.
5. **Shell — тонкий складальник** → міграція оболонки чи додавання headless CLI (другий «shell» поверх того самого `app`) не чіпає жодного шару нижче.

Контроль: заборонені залежності перевіряються в CI автоматично (аналіз графа крейтів/імпортів); порушення = червоний білд, без винятків за домовленістю.
