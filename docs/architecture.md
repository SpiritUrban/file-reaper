## 0. Архітектурні драйвери (що диктує продукт)

Архітектура виводиться з чотирьох продуктових вимог, і кожне рішення нижче має відповідати хоча б одній з них:

| Драйвер | Наслідок для архітектури |
|---|---|
| **D1. Цифра «N ГБ можна звільнити» — за секунди, не хвилини** | Сканування метаданих відділене від «важких» операцій (хешування, превью). Перша відповідь будується лише на метаданих. Прогресивна видача — стрімінг результатів у UI під час скану. |
| **D2. Нуль браузингу: продукт показує категорії, не диск** | Центральна абстракція — не «файлова система», а **індекс кандидатів**. Детектори працюють над індексом; UI ніколи не звертається до диска напряму. |
| **D3. Рішення за превью: великі превью, миттєві при наведенні (Live Preview)** | Окремий конвеєр превью з пріоритетною чергою (видиме → прогнозоване → фонове) і стійким дисковим кешем. |
| **D4. Безпека: жодної безповоротної втрати даних** | Quarantine — транзакційна підсистема з журналом. Видалення — двофазне. Незнищуваний інваріант: файл не зникає з диска, поки не пройшов через Quarantine з записом у журналі. |

Продукт **не** потребує: дерева каталогів, довільної навігації по диску, операцій файлового менеджера. Це спрощує архітектуру — ми оптимізуємо один конвеєр, а не універсальний доступ до FS.

## 1. Загальна архітектура системи

### 1.1. Двопроцесна модель: UI ↔ Core Engine

Система складається з двох чітко розділених частин:

- **Core Engine (нативне ядро)** — вся робота з диском: сканування, індексація, детектори, хешування, превью, Quarantine. Багатопотоковий, працює у фоні, не залежить від стану UI.
- **UI (webview-шар)** — лише відображення і введення. Не має прямого доступу до файлової системи. Отримує дані виключно з Core через IPC.

```
┌────────────────────────────  UI (webview)  ─────────────────────────────┐
│  Cleanup Summary · Категорії · Сітка · Live Preview · Quarantine · ...  │
│        ▲ підписки на події (стрім)          │ команди (запити)          │
└────────┼────────────────────────────────────┼───────────────────────────┘
         │                IPC (events / commands)                          
┌────────┼────────────────────────────────────▼───────────────────────────┐
│                            CORE ENGINE (нативний)                       │
│                                                                         │
│  ┌──────────┐   ┌──────────┐   ┌────────────────┐   ┌───────────────┐   │
│  │ Scanner  │──▶│  Index   │──▶│ Detector Farm  │──▶│  Aggregator   │   │
│  │ (обхід)  │   │ (SQLite+ │   │ (категоризація,│   │ (цифри, групи,│   │
│  └──────────┘   │  memory) │   │  дублікати)    │   │  сортування)  │   │
│                 └──────────┘   └────────────────┘   └───────────────┘   │
│  ┌────────────┐  ┌─────────────┐  ┌────────────┐  ┌──────────────────┐  │
│  │ Preview    │  │ Quarantine  │  │ Settings   │  │ Cache Manager    │  │
│  │ Pipeline   │  │ Service     │  │ Service    │  │ (хеші, превью,   │  │
│  └────────────┘  └─────────────┘  └────────────┘  │  метадані, USN)  │  │
│                                                   └──────────────────┘  │
└──────────────────────────────────────────────────────────────────────────┘
```

### 1.2. Модель взаємодії: команди + стрім подій

- **Команди** (UI → Core): «сканувати диски», «відкрити категорію», «позначити», «reap», «відновити». Всі — неблокуючі: команда повертає підтвердження прийняття, результат приходить подіями.
- **Події** (Core → UI): «цифра оновилась», «категорія поповнилась», «превью готове», «скан завершено», «файл переміщено у Quarantine». UI — реактивний споживач стріму.
- **Пагінація по запиту:** сітка категорії запитує «вікно» елементів (видимий діапазон + запас), а не всю категорію. Категорія на 50 000 файлів не передається через IPC цілком ніколи.
- **Тротлінг подій:** оновлення лічильників агрегуються Core-ом (напр., не частіше 10 разів/с), щоб стрім подій не задушив UI під час швидкого скану.

### 1.3. Ключовий принцип: UI можна вбити будь-коли

Core Engine не тримає стан у UI. Скан, хешування, автоочищення Quarantine переживають перезапуск інтерфейсу. Це також відкриває шлях до майбутнього headless-режиму (CLI/автоматизація) без зміни ядра.

## 2. Архітектура сканування файлової системи

Сканування — найкритичніша до швидкості підсистема (драйвер D1). Архітектура: **два шляхи скану + один потік результатів**.

### 2.1. Швидкий шлях: читання MFT (NTFS)

- Для NTFS-томів (переважна більшість Windows-дисків ЦА) сканер читає **Master File Table напряму**, а не обходить каталоги рекурсивно. Це дає метадані *всіх* файлів тому (ім'я, розмір, дати, шлях) за секунди навіть для мільйонів файлів — на порядок-два швидше за обхід каталогів.
- Потребує прав адміністратора. Стратегія: просити elevation при першому запуску з поясненням вигоди; за відмови — падати на повільний шлях.

### 2.2. Резервний шлях: паралельний обхід каталогів

- Для не-NTFS томів, мережевих винятків і роботи без elevation — класичний обхід, але паралельний: пул воркерів розбирає чергу каталогів (work-stealing), глибина не обмежує паралелізм.
- Виключені шляхи (системні каталоги, список користувача з Налаштувань) відсікаються на рівні обходу — у виключені піддерева сканер взагалі не заходить.

### 2.3. Інкрементальний рескан: USN Journal

- Після першого повного скану повторні НЕ скануються з нуля: сканер читає **USN Change Journal** NTFS — журнал змін тому — і оновлює індекс лише для файлів, що змінилися з моменту останнього скану.
- Наслідок для UX: другий і наступні запуски програми показують актуальну цифру «можна звільнити» майже миттєво.
- Якщо журнал перезаписано (надто давно не запускались) — авто-фолбек на повний скан.

### 2.4. Потік результатів

- Сканер віддає метадані **батчами** (тисячі записів), а не по одному файлу — мінімізація синхронізації.
- Порядок видачі оптимізовано під D1: спочатку метадані, що найшвидше наповнюють найважчі категорії (великі файли спливають першими).
- Скан переривається миттєво (кооперативна відміна на межах батчів); частковий результат залишається валідним у індексі.

## 3. Архітектура індексації

### 3.1. Роль індексу

Індекс — **єдине джерело правди** для всіх детекторів і UI. Формула: *сканер пише в індекс, детектори читають з індексу, UI читає з агрегатів*. Ніхто, крім сканера і Quarantine, не торкається реальної FS.

### 3.2. Дворівнева структура

| Рівень | Що зберігає | Навіщо |
|---|---|---|
| **In-memory (гарячий)** | Компактні записи метаданих поточної сесії: шлях (інтернований), розмір, дати, тип, прапорці категорій | Швидкість детекторів і сортувань: мільйони записів обробляються без звертань до диска |
| **Persistent (SQLite, WAL-режим)** | Повний індекс + обчислені дорогі атрибути: хеші, вердикти дублікатності, посилання на превью-кеш, рішення користувача («keep») | Переживає перезапуск; інкрементальний рескан оновлює лише дельту; «keep»-рішення не забуваються |

- Схема БД версіонується з міграціями від першого релізу.
- Запис — батчевий, через одну чергу (SQLite — однописьменний), читання — паралельне.

### 3.3. Що індексується

Тільки те, що потрібно детекторам: метадані + обчислені атрибути. Вміст файлів НЕ індексується (ми не пошуковик). Повнотекстовий пошук за іменем/шляхом — по індексу, тому «пошук серед кандидатів» з верхньої панелі миттєвий.

### 3.4. Життєвий цикл запису

```
знайдений сканером → у пам'яті → категоризований → (опц.) хешований
     → показаний у UI → рішення користувача:
         keep  → прапорець в індексі, схований з кандидатів
         reap  → передається Quarantine, в індексі позначений як "у карантині"
```

## 4. Архітектура пошуку дублікатів

Наївне «похешувати все» на диску 1 ТБ — години читання. Архітектура — **каскад фільтрів**, де кожен щабель дешевший за наступний і радикально звужує множину:

```
УСІ ФАЙЛИ (з індексу, метадані вже є — 0 читань диска)
  │  щабель 1: групування за точним розміром
  ▼     розмір унікальний → НЕ дублікат, відкинуто (~95% файлів)
ГРУПИ ОДНАКОВОГО РОЗМІРУ
  │  щабель 2: частковий хеш (перші + останні 64 КБ кожного файла)
  ▼     хеш відрізняється → відкинуто (читання: КБ, не ГБ)
ГРУПИ-КАНДИДАТИ
  │  щабель 3: повний хеш (BLAKE3, потоково, багатопотоково)
  ▼     лише тут читається весь файл — і лише для реальних претендентів
ПІДТВЕРДЖЕНІ ГРУПИ ДУБЛІКАТІВ → категорія «Дублікати»
```

Ключові рішення:

- **Прогресивність:** щаблі 1–2 дають попередню цифру категорії швидко; UI маркує її як «уточнюється», щабель 3 підтверджує у фоні. Цифра «27 ГБ дублікатів» не чекає повного хешування тома.
- **Кеш хешів** (розділ 10): хеш зберігається в індексі з розміром+датою зміни файла; незмінені файли між сесіями не перехешовуються. Перший скан — найдорожчий, наступні — копійки.
- **Пріоритет великих груп:** хешування йде від найбільших за потенційним звільненням груп — найцінніші дублікати підтверджуються першими.
- **Розумний дефолт «який залишити»** — політика (найстаріший шлях / поза Downloads / налаштовується) обчислюється Aggregator-ом, UI лише показує.
- Повний хеш обмежується конфігурованим стелею одночасних читань на **том** (не глобально): паралельне читання двох дисків — так, конкуренція за один шпиндель/SSD-шину — ні.

## 5. Архітектура генерації прев'ю

Превью — головний інструмент рішення (D3), і головний ризик продуктивності. Архітектура: **пріоритетна черга + дворівневий кеш + деградація якості**.

### 5.1. Пріоритетна черга

Всі запити превью падають в одну чергу з пріоритетами:

| Пріоритет | Джерело | Ціль латентності |
|---|---|---|
| P0 | Файл під курсором у Live Preview (правий монітор) | < 100 мс |
| P1 | Видимі плитки поточної сітки | < 500 мс |
| P2 | Префетч: 2–3 плитки за напрямом руху курсора / наступний скрол-екран | до появи на екрані |
| P3 | Фонова генерація для топ-N найбільших кандидатів кожної категорії | коли простоюємо |

Запити застарівають: якщо користувач поїхав далі — P0/P1 запити на вже невидимі файли скасовуються, не досиджують чергу.

### 5.2. Джерела превью (за швидкістю)

1. **Кеш TrashRadar** (дисковий) — миттєво.
2. **Системний кеш мініатюр Windows** (Shell thumbnail API) — дуже швидко, покриває більшість зображень/відео, які користувач колись бачив у Explorer.
3. **Власна генерація**: зображення — декодування з даунскейлом; відео — витяг ключових кадрів (вбудований декодер на базі ffmpeg-функціональності): один кадр для плитки, смуга з 10–20 кадрів для скраб-прев'ю.
4. **Нема превью** (архів, ISO, бінарник) — UI рендерить типізовану плитку сам, Core не залучається.

### 5.3. Дворівневий результат

Для великого превью (Live Preview, весь монітор): спочатку віддається кешована мініатюра, розтягнута (миттєво, розмито), паралельно генерується повнорозмірна — і підміняє її. Око отримує відповідь < 100 мс завжди; різкість доганяє за пів секунди. Скраб відео працює по попередньо витягнутій смузі кадрів, а не декодує на льоту.

### 5.4. Ізоляція збоїв

Декодери медіа — найнестабільніший код у системі (биті файли, екзотичні кодеки). Генерація превью працює в ізольованих воркерах: краш декодера на битому файлі позначає файл «превью недоступне» і не валить ні скан, ні застосунок.

## 6. Архітектура категоризації файлів

### 6.1. Модель: ферма незалежних детекторів

Кожна категорія з product.md — **окремий детектор** з єдиним контрактом: *отримує потік записів індексу → повертає вердикти «кандидат / ні» з поясненням і оцінкою безпечності*.

| Детектор | Тип логіки |
|---|---|
| Великі файли, Старі файли, Забуті відео, Архіви, Інсталятори/ISO | **Предикатні**: правила над метаданими (розмір/вік/тип/шлях). Миттєві, працюють у потоці скану |
| Тимчасові файли, Кеші програм | **Локаційні**: базуються на реєстрі відомих шляхів (Temp-каталоги, кеш-каталоги популярних програм). Реєстр — декларативні дані, оновлюється без релізу коду |
| Артефакти розробки (node_modules, build/dist, Unity Library) | **Структурні**: розпізнають патерн каталогу (маркерні файли поруч: package.json, Assets/ тощо) + обчислюють «активність проєкту» за датами сусідів. Вердикт — на цілу папку як одиницю |
| Дублікати | **Обчислювальний**: окремий конвеєр (розділ 4), найдорожчий, працює після предикатних |

### 6.2. Вердикт детектора — це не лише «так/ні»

Кожен вердикт містить: категорію, **пояснення** («відео 4.2 ГБ, останній доступ 8 міс тому») — воно ж рядок детектора в UI, та **рівень безпечності** (safe-to-bulk / review-recommended) — саме він вмикає кнопку [Позначити все] на категорії й маркер «?» на екрані підтвердження.

### 6.3. Перетини і перерахунок цифри

Файл може бути у кількох категоріях (старе відео + дублікат). Aggregator тримає це чесним: **загальна цифра «можна звільнити» — це сума унікальних файлів**, не сума категорій. Рішення (keep/reap) застосовується до файла і миттєво відбивається в усіх категоріях.

### 6.4. Конфігурованість

Пороги детекторів (мін. розмір, вік) — параметри, які UI змінює «на льоту» з рядка детектора; предикатні детектори перераховуються з індексу за мілісекунди без рескану диска. Архітектура детектора-як-контракту напряму готує ґрунт для «власних категорій» з roadmap (Хвиля 1).

## 7. Архітектура Quarantine

### 7.1. Фізична модель: перейменування, не копіювання

- На кожному томі створюється прихований службовий каталог (напр. `<том>\.trashradar\quarantine\`).
- «Видалення» = **move у межах того самого тому** = атомарне перейменування запису MFT. Миттєво навіть для 60 ГБ файла, нуль копіювання, нуль зносу SSD.
- Наслідок, зафіксований ще в product.md: місце фактично звільняється при очищенні Quarantine. Прогноз «диск після очищення» Aggregator рахує завжди.
- Файли у карантинному каталозі зберігаються під суррогатними іменами (ID запису журналу) — жодних конфліктів імен.

### 7.2. Журнал Quarantine (manifest)

Окрема таблиця в SQLite — **транзакційний журнал**, для кожного запису: оригінальний повний шлях, суррогатне ім'я, розмір, дата поміщення, дата згорання (TTL), статус (`quarantined / restored / purged`). Журнал — джерело правди для екрана Quarantine, таймерів згорання і відновлення.

### 7.3. Операції

- **Reap:** для кожного файла — транзакція: запис у журнал зі статусом «в процесі» → move → підтвердження статусу. Збій на середині завжди відновлюваний: при старті Core звіряє «в процесі»-записи з реальністю і докочує або відкочує.
- **Restore:** зворотний move на оригінальний шлях (шлях зайнятий → відновлення з суфіксом і подія-попередження в UI).
- **Purge (згорання):** фонове завдання-«двірник» періодично знищує записи з простроченим TTL. Єдине місце в системі, де файл справді зникає.
- **«Скасувати» з тоста** після Reap — це масовий Restore останньої операції: журнал групує reap-и в batch із спільним ID.

### 7.4. Межі

Quarantine-каталог виключений зі сканування (сміття не знаходить саме себе). Файли з томів без права запису в службовий каталог у MVP просто не отримують кнопку reap (чесне обмеження замість небезпечного фолбеку на копіювання).

## 8. Архітектура безпечного видалення

Безпека — наскрізний інваріант (D4), реалізований шарами:

1. **Єдиний шлюз.** У Core існує рівно один модуль з правом змінювати FS деструктивно — Quarantine Service. Сканер, детектори, превью — фізично read-only. Purge викликається лише зсередини Quarantine Service.
2. **Двофазність.** Користувацьке «видалити» ніколи не знищує дані: фаза 1 — reap (оборотний move + журнал), фаза 2 — purge (по TTL або явною командою на екрані Quarantine, єдине місце з жорстким підтвердженням).
3. **Guard-list.** Незалежно від вердиктів детекторів, шлюз відмовляється чіпати: системні каталоги Windows, каталоги встановлених програм, власні файли TrashRadar, том без Quarantine-каталогу. Це остання лінія оборони — навіть баг у детекторі не призведе до reap системного файла.
4. **Перевірка ідентичності перед move:** файл звіряється (розмір + дата зміни) з тим, що бачив індекс. Файл змінився після скану → операція для нього скасовується з подією в UI (хтось ним користується — він більше не «забутий»).
5. **Журнал усіх деструктивних операцій** append-only: що, коли, звідки, за чиєю командою (reap / TTL / ручний purge). Це і аудит для довіри користувача, і матеріал для діагностики.

## 9. Архітектура налаштувань

- **Один файл конфігурації** у профілі користувача, людиночитаний формат, версіонована схема з міграціями. Жодного реєстру Windows.
- **Шари значень:** дефолти вшиті в Core → файл користувача містить лише відхилення від дефолтів (легкі апгрейди, маленький файл, просте «скинути»).
- **Власник — Core, не UI.** UI змінює налаштування командою; Core валідує, застосовує, розсилає подію «конфіг змінився». Гаряче застосування без перезапуску: зміна порога детектора → перерахунок категорій з індексу; зміна TTL → перепланування згорань.
- **Склад:** параметри Quarantine (розташування, TTL, поріг попередження), сканування (виключені шляхи, мін. розмір), пороги і перемикачі кожного детектора, користувацькі шаблони, гарячі клавіші, поведінка Live Preview (дефолтна озброєна дія, таймаут розрядження), геометрія вікна/межі зон.
- «Keep»-рішення і стан індексу — НЕ налаштування: вони живуть у БД індексу. Файл конфігурації можна переносити між машинами.

## 10. Архітектура кешування

Кешування — те, що перетворює «швидко один раз» на «швидко завжди». Чотири незалежні кеші під управлінням Cache Manager:

| Кеш | Зберігання | Ключ валідності | Що дає |
|---|---|---|---|
| **Індекс метаданих** | SQLite | USN Journal (позиція в журналі змін тому) | Повторний запуск: актуальна цифра за секунди без повного скану |
| **Кеш хешів** | SQLite (в індексі) | розмір + дата зміни файла | Дублікати між сесіями майже безкоштовні |
| **Кеш превью** | Файли на диску (мініатюри, кадри, скраб-смуги) + записи в індексі | розмір + дата зміни джерела | Миттєвий Live Preview для вже бачених файлів |
| **Кеш агрегатів** | Пам'ять | Інвалідується подіями індексу | Цифри категорій і сортування без перерахунку на кожен запит UI |

Політики:

- **Бюджет розміру:** превью-кеш має стелю (налаштовується), витіснення LRU. Кеш чистильника дисків не має права сам бути проблемою — власний розмір TrashRadar показується у Налаштуваннях з кнопкою очищення.
- **Валідність без довіри:** будь-який кешований запис перед використанням у деструктивній операції перевіряється проти живої FS (розділ 8, п.4). Кеш прискорює показ — рішення видалити завжди звіряється з реальністю.
- **Деградація:** втрата/пошкодження будь-якого кешу — не помилка, а холодний старт відповідної підсистеми.

## 11. Tauri vs Electron

### 11.1. Порівняння у контексті TrashRadar

| Критерій | Tauri | Electron | Вага для нас |
|---|---|---|---|
| **Мова ядра** | Rust — нативна швидкість, паралелізм без гонок даних, прямий доступ до WinAPI (MFT, USN, move-семантика) | Node.js — I/O-bound ок, але CPU-важке (хешування, декодування) потребує нативних аддонів або воркерів; прямий WinAPI — через FFI-прошарки | **Критична**: сканер, хеші, превью — саме CPU/IO-важкі нативні задачі |
| **Пам'ять/розмір** | ~10–40 МБ RAM (системний WebView2), інсталятор ~5–10 МБ | 150–400+ МБ RAM (вбудований Chromium), інсталятор 80–150 МБ | **Висока**: ми фонова утиліта поруч з Premiere/Unity/грою; ЦА (power users) зневажає «ще один Chromium» |
| **Довіра ЦА** | «Написано на Rust» — маркетинговий актив у dev-аудиторії | Стигма «Electron-додаток» у power users | Середня, але реальна |
| **Безпека архітектури** | UI ізольований від FS за замовчуванням; кожна можливість ядра — явно оголошена команда | Повний доступ Node з renderer легко «протікає»; ізоляцію треба дисципліновано будувати | **Висока**: для програми, що видаляє файли, «UI фізично не може чіпати диск» — властивість, а не домовленість |
| **Екосистема UI** | Той самий web-стек (будь-який фреймворк) | Той самий web-стек + більше готових desktop-рецептів | Паритет для нашого UI |
| **Зрілість/ризики** | Молодша; WebView2 оновлюється системою (версійний дрейф рендерера); менше готових відповідей | Дуже зріла; Chromium зафіксований з застосунком | Середня — WebView2 на Win10/11 передвстановлений і evergreen; наш UI не використовує екзотичних web-API |
| **Багатовіконність/два монітори** | Достатня: кілька вікон, керування геометрією | Багатша | Низька: наш Live Preview — одне розтягнуте вікно (по ui.md), це вміють обидва |
| **Крос-платформність майбутня (macOS)** | Так | Так | Паритет |

### 11.2. Рішення

**Обираємо Tauri: Rust-ядро + системний WebView2.**

Вирішальний аргумент — **збіг ваги ядра і UI у продукті**. TrashRadar — це на 80% нативний рушій (MFT-скан, USN, каскад хешування, декодування кадрів, транзакційний Quarantine) і на 20% реактивний UI-тонкий-клієнт. Rust — природна мова для цих 80%; Electron довелося б доукомплектовувати нативними модулями, отримавши складнішу збірку і гіршу базову лінію по пам'яті. Двопроцесна модель розділу 1 лягає на Tauri без насильства: Core = Rust-процесна частина, UI = webview, IPC = вбудовані команди/події.

Прийняті ризики і їх пом'якшення:

- *Молодша екосистема* → вся складна логіка живе у чистому Rust-ядрі, незалежному від Tauri; Tauri — лише обгортка вікна та IPC. Міграція обгортки (якщо колись знадобиться) не чіпає рушій.
- *Дрейф версій WebView2* → UI тримаємо на консервативних web-можливостях; смоук-тести на мінімально підтримуваній версії WebView2.

## 13. Фонові модулі

Модулі Core, що працюють без участі користувача (усі — з кооперативною відміною і пріоритетом нижче за інтерактивні запити):

| Модуль | Коли працює | Що робить |
|---|---|---|
| **Scanner** | Старт застосунку; ручний рескан; за USN-подіями | Наповнює/оновлює індекс |
| **Duplicate Hasher** | Після предикатних детекторів, у простої | Каскад хешування (розділ 4) |
| **Preview Worker Pool** | Постійно | Розбирає пріоритетну чергу превью (P0–P3) |
| **Quarantine Sweeper** | Планувальник (перевірка кілька разів на добу + при старті) | Purge прострочених записів; попередження «Quarantine > N ГБ» |
| **Cache Janitor** | У простої | LRU-витіснення превью-кешу, вакуум БД, чистка сирітських файлів кешу |
| **Change Monitor** | Постійно (легкий) | Слухає USN Journal: підтримує індекс і цифру актуальними, поки програма відкрита |
| **Crash Recovery** | Лише при старті | Докочує/відкочує незавершені транзакції Quarantine (розділ 7.3) |

Політика ресурсів: фонові модулі самообмежуються (низький пріоритет I/O та CPU у ОС), щоб TrashRadar ніколи не заважав рендеру відео чи грі, які працюють поруч.

## 14. Асинхронні операції

Правило: **будь-яка операція, що торкається диска або може тривати > 16 мс, — асинхронна.** Синхронними залишаються лише обчислення над даними в пам'яті UI.

Обов'язково асинхронні (неблокуючі для UI, з подіями прогресу):

- сканування (повне, інкрементальне) і будь-який перерахунок детекторів;
- хешування дублікатів — усі щаблі;
- генерація та завантаження превью (включно з P0: навіть 100-мс ціль — це async з підміною плейсхолдера);
- всі операції Quarantine: reap, restore, purge — батчами, з прогресом для великих пакетів (reap 8 000 тимчасових файлів — це подієвий процес зі смужкою, не «завислий клік»);
- запити «вікон» даних для сітки (пагінація);
- запис налаштувань і будь-який запис у SQLite;
- обчислення прогнозу «диск після очищення».

Наслідки для UX, зафіксовані як контракти:

- UI-потік ніколи не чекає Core: кожна дія користувача має миттєву оптимістичну реакцію (плитка позначилась одразу; якщо Core відхилив — відкат з поясненням).
- Скасовуваність: скан, хешування, превью-запити скасовуються миттєво; reap-батч можна перервати на межі файла — вже переміщене залишається у Quarantine (валідний стан, бо оборотний).

## 15. Швидка робота на дисках понад 1 ТБ

Стратегія: **жодна підсистема не має вартості, пропорційної повному обсягу диска, на гарячому шляху.** Розкладка по вузьких місцях:

1. **Метадані, не вміст.** Перша цифра «можна звільнити» будується виключно з метаданих (MFT-скан): для 1–4 ТБ тому з мільйонами файлів це секунди. Читання вмісту (хеші, превью) — тільки відкладено, тільки для звуженої множини кандидатів.
2. **MFT замість обходу, USN замість рескану** (розділ 2): вартість першого знайомства з томом — O(кількість записів MFT), вартість кожного наступного запуску — O(кількість змін). Обсяг тома у терабайтах на це майже не впливає — впливає кількість файлів.
3. **Каскад дублікатів** (розділ 4): повне читання лише для груп, що пройшли фільтри розміру і часткового хешу. На типовому диску це одиниці відсотків обсягу. Хешування великих файлів — потокове (константна пам'ять) і паралельне по ядрах.
4. **Превью — тільки на вимогу** з пріоритетною чергою: система ніколи не генерує «всі превью диска»; вона генерує видимі, прогнозовані та топ найбільших. Кеш робить повторні сесії миттєвими.
5. **Пам'ять під контролем:** in-memory індекс — компактні структури (інтерновані шляхи, числові атрибути), ціль — сотні МБ навіть на 5+ млн файлів; все, що більше, — у SQLite з віконними запитами. UI тримає лише видиме вікно сітки (віртуалізація) — категорія на 100 000 файлів коштує стільки ж, скільки на 100.
6. **Дисковий паралелізм з обмеженням на том:** паралельні черги I/O на кожен фізичний том, стеля одночасних операцій на том — максимум пропускної здатності без самоконкуренції на одному носії.
7. **Тротлінг стріму до UI:** при знаходженні 50 000 файлів/с UI отримує агреговані дельти 10 разів/с — рендер не стає вузьким місцем скану.

Цільові показники (перевіряються на еталонних машинах ЦА):

| Метрика | Ціль |
|---|---|
| Перша цифра + перші наповнені категорії (NTFS, 1 ТБ, ~1.5 млн файлів, теплий диск) | < 10 с від запуску |
| Повторний запуск (USN-дельта) | < 2 с до актуальної цифри |
| Превью P0 (Live Preview, кеш) / (генерація) | < 100 мс / < 600 мс до чорнової якості |
| Reap 1 000 файлів на одному томі | < 2 с |
| RAM Core у простої після скану 1 ТБ | < 300 МБ |

## 16. Відкриті питання (для етапу реалізації)

1. Політика elevation: просити адмін-права постійно (маніфест) чи сесійно (тільки для MFT-скану)? Впливає на UX першого запуску.
2. Мінімальна межа часткового хешу для щабля 2 дублікатів (64 КБ — стартова гіпотеза, потребує бенчмарків на реальних медіатеках).
3. Формат зберігання скраб-смуг відео (окремі кадри vs спрайт-смуга) — залежить від замірів латентності WebView2.
4. Чи потрібен окремий процес для превью-воркерів (повна ізоляція крашів) або досить потокової ізоляції з панік-бар'єрами — вирішать перші стрес-тести на битих медіафайлах.
